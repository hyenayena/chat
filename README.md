# chat

Provider-neutral chat for yena: the chat contract (the events a chat engine emits, the session controller a UI drives, the permission requests a provider raises) and the chat UI (the views, moved from `claude` in CHAT-2).

It is a yena plugin (`runtime: "node"`, `entry: src/index.ts`, `install: bin/install`, version 0.5.6): it registers the gallery sections and adds the `chat` and `fix` commands. It depends on core only and has no credentials; its data directory holds `prefs.json` and `exports/`. Its one npm dependency is highlight.js 11.12.0 (exact pin; see Development).

## Commands (`src/commands.ts`)

`chat [subcommand] [args…]` (`agent: deny`, autostart). Without a subcommand it opens a new chat that attaches to a background chat when one runs. The own subcommands, with their policies:

- `deny`: `new [--provider <id>] [model]`, `continue`, `ask [--new] <text…>`, `resume [session]`, `rewind`, `fork`, `copy [n]`.
- `confirm`: `start [--provider <id>] <message…>` (20 000 characters at most), `send <message…>`, `rename <name…>`, `export [file]`, `stop [session]`.
- `safe`: `tasks`, `mcp [subcommand]` (`mcp reconnect <server>` inherits), `session`, `sessions`.
- Any command of the open chat (its `commands`, else the default provider's `commandHints()`) is a passthrough subcommand: `chat compact` sends `/compact` to the chat. The own names win; the passthrough declares no policy and inherits `deny`.
- `fix` (`agent: deny`) starts a chat like `chat start` with the dev-start failure record as the message.

The providers are registered by other modules (`registerChatProvider`); the default one is the saved one or the first. With none, every command that needs one fails with `No chat provider is installed`.

**Origin** (`src/origin.ts`): no `ctx.signal` is `user`, `ctx.caller === 'yena'` is `assistant`, anything else (a missing caller included) is `unattended`. Every open, ask and send passes it. A provider treats everything that is not `user` or `assistant` as key-only. `chat send` into the open chat from a non-interactive origin calls `OpenedChat.admitSend(origin)`; when the provider has none, it is refused with `The open chat does not take messages from unattended runs`. The same check guards a passthrough command.

**Open flow** (`src/hub.ts`, `src/open-flow.ts`): replacing a chat runs `provider.admit(origin)` first (a refusal leaves the open chat untouched), then ends an idle background chat (unless attaching), closes the previous chat, and opens the new one. The view half (files, the `ChatView`, history replay, banner, shell panel, the closing line) is here; the provider opens the session. `chat` closes then flushes an opened chat exactly once.

**Prefs** (`<dataDir>/prefs.json`, `{v: 1, permissionMode?, inputMode?, keepRunning?, provider?}`, written atomically): an invalid file is ignored. When the file is missing and a provider is registered, the first non-empty `legacyPrefs()` is written once and then `clearLegacyPrefs()` runs on each provider; a failed write clears nothing and logs `prefs hand-over failed`. The `Chat` settings tab has Permission mode (the options follow the default provider's modes), Input mode, Keep working after exit and Default provider.

**Exports** go to `<dataDir>/exports/<YYYY-MM-DD-HH-MM>-<session8>.md`, or to a file inside the provider's project directory; the path must stay inside one of the two and an existing file is never overwritten.

## For other modules

Import `src/public.ts` through your own `src/deps/chat.ts` and declare `chat` in your `yena.json` dependencies with a range (`{"source": "chat", "version": "^0.5.0"}`). Fields in the contract are optional: a provider that lacks a feature does not emit it. Never rename a field: the claude module's runner protocol (version 1) carries these shapes on the wire.
Import `src/public-ui.ts` only through a lazily loaded adapter, so `ping`, `ask` and the background runner never load React or Ink (chat's own open flow is the one that loads it; claude loads no UI).

### Module sessions

`openSession(req)` and `collectAnswer(session, text, opts?)` (in `public.ts`, types in `src/contract/module-session.ts`) let a module run a background conversation through a registered provider and read the final answer. The event readers (`readChatEvent`, `readUiEvent`, `readPermissionRequest`, `readPermissionDecision`, `ContractError`) are exported too.

The rules fail closed:
- The origin is always `module` (key-only: the provider admits an API key only). It never attaches to a running runner, never waits for a lock and gets no console commands.
- `mode` is `default` or `plan`. The handle has no allow path: only `deny(id)` and cancel. An allow comes from the user's keypress in `createPermissionElement({session, request, host?, onDone?, armMs?})` (public-ui), which hides the "always" choice.
- `prompts: 'deny'` (default) denies every request at once; `'show'` keeps them for the element and cancels each after `promptTimeoutMs` (default 15 min, 1 s..1 h).
- `collectAnswer` times out after `timeoutMs` (default 10 min, 1 s..1 h) or on an aborted signal, cancelling pending requests and interrupting. An idle session ends after `idleTimeoutMs` (default 15 min, 10 s..1 h); `end()` is idempotent.
- One session per process: it is refused while the user's chat is open or opening; the user's `chat` ends a running one, and its `collectAnswer` resolves `interrupted` with `The user opened a chat`.
- Text from the provider is scrubbed: `collectAnswer` returns scrubbed text, and `session.scrub(text)` is for anything shown from `subscribe`.

```ts
const session = await openSession({owner: 'clan', mode: 'plan'});
try {
	const {outcome, text} = await collectAnswer(session, 'Summarize the plan', {signal});
	if (outcome === 'ok') use(text);
} finally {
	await session.end();
}
```

### Activity in the console panel

The user's chat (`chat:user`) and each module session (`chat:module-<owner>`, label `chat · <owner>`) report `running` while they answer, `ok` after an idle turn and `gone` when they end, through core's `reportActivity` on the host bus (`src/activity.ts`). Only sessions this yena holds are shown.

## Provider API

`src/contract/provider.ts` (pure, in `public.ts`) is what a chat provider implements; `src/registry.ts` is where it registers. The `chat` and `fix` commands and the open flow call the default provider (`src/hub.ts`, `src/commands.ts`).

- `registerChatProvider(provider)` returns a function that removes only that registration, or `undefined` when the provider is refused (the caller logs it): the id must match `/^[a-z][a-z0-9-]{0,31}$/`, `label` is a non-empty string of at most 40 characters, `open`, `admit` and `ask` are functions, and the first registration of an id wins. `chatProviders()` lists `{id, label}` in registration order; `chatProvider(id)` returns the provider.
- `Origin` (`user`, `assistant`, `unattended`, `module`) says who asks. `isInteractive(origin)` is true for `user` and `assistant` only; a value it does not know counts as not interactive. A provider that may run without the user at the keyboard must refuse a subscription for such an origin (Anthropic's rules) and say why.
- `ChatProvider` has `admit(origin)` (throws when a chat may not be opened now, before the open chat is replaced), `open(request, env)` (returns an `OpenedChat`, or `undefined` when the user cancelled while it waited), the session list and history (`sessions`, `history`, `prompts`, `detail`, `title`, `rename`, `lastSession`, `projectDir`), `running()` and `stop()`, `ask(request, env)`, `commandHints()`, `describe()`, `validModel()` and the optional `legacyPrefs()` and `clearLegacyPrefs()`.
- `OpenedChat.close()` is followed by exactly one `await flush()`; the provider frees its locks at the end of `flush`. `admitSend(origin)` throws when a message from that origin may not go into this chat.
- `ChatSession` extends `ChatController`; every extra member (`commands`, `tasks`, `stopTask`, `mcpStatus`, `reconnectMcp`, `rewindFiles`, `setTitle`, `setKeep`, `usage`, `end`) is optional.

## The chat UI (`src/ui/`)

The plugin (`src/index.ts`) registers the gallery sections `chat`, `diff`, `tools`, `status`, `plan`, `layout` and `markdown` (`registerGallerySection`, first registration wins). A section that does not register logs `gallery section skipped`; the plugin still works.
The views are provider-neutral: the chat, its transcript, the markdown and tool and file cards, the prompts, the agent panel, the plan widget, the status bar and the input line (with vim mode). Claude's engine and runner stay in `claude`, the provider that opens sessions for these views (see `claude/chat.md` in the architecture folder).

Next to core's console (`control.host` present) the chat reads keys only while focused, lays out in the width the host gives, ignores the console toggle (`§` or Ctrl+T, via `host.isHostKey(input, key)`), ignores core's host keys (Shift+←/→ move the focus, Ctrl+T toggles the console); Tab with no `@`/`/` suggestion list open opens or closes the console (`host.togglePanel()`), with a list it completes, Shift+Tab cycles the mode, moves the input to the console with → on an empty draft, and Esc never leaves it (only Ctrl+C does) and never opens the console: Esc clears the draft or interrupts, and does nothing while an interrupt is pending.

Keys:
- Enter sends. Alt+Enter or Shift+Enter inserts a newline; a bracketed paste is inserted sanitized and never submitted. The input soft-wraps by words over up to 10 rows (half the free space at most; widths by grapheme, wide characters count as two), so all of a typed line stays visible; a longer text keeps the cursor's rows in view. In permission prompts and questions the header, the options and the key hint wrap instead of being cut, and the typed `Your answer:` / `Reason:` wraps under its label; the framed body gives up the rows they take. Input is limited to 32000 characters (`Input truncated to 32000 characters`).
- Esc while an answer runs interrupts it; the next message continues the same conversation. In the first 10 s of a turn Esc interrupts at once; after that the first Esc only shows `Press Esc again to interrupt` and a second Esc within 2 s interrupts, so a stray Esc (a split mouse report, for example) does not end a long turn (TASK-30; `escapeInterrupts` in `src/ui/ChatView.tsx`). Esc while idle clears the draft, or leaves the chat when the draft is empty. Ctrl+C interrupts a running answer at once, or leaves the chat when idle.
- Enter while an answer runs hands the message to that answer: Claude reads it between steps (see Input below).
- `:q` (or `:q!`) as the whole message exits yena (through `host.quit()`; without a host it leaves the chat); it is never sent.
- Slash lines (needs core 0.6.0+ `ViewHost.runLine`/`listCommands`, feature-detected in `src/ui/view-commands.ts`; on an older core every line goes to Claude): a one-line `/<command> [args]` whose first word is a yena console command runs in the console (which opens beside the chat, the input stays in the chat; the chat prints a dim `/<line> → console`), e.g. `/project list`, `/settings`, `/chat`. `//text` sends `/text` to Claude. Any other line, a `/word` that is not a console command included, is sent to Claude as written (`client_composed`, so Claude Code does not run it as a command; such a turn also skips Claude Code's per-turn attachments). Typing `/` lists the matching console commands with their descriptions above the input (`src/ui/slash.ts` `slashHints`; prefix matches first, at most 6): ↑/↓ choose, Tab takes the highlighted one, Enter takes it too unless the typed name is complete or the line ends with a space (then Enter runs it), Esc hides the list. After a command and a space the list goes on with its subcommands (aliases count too), e.g. `/claude ` lists the chat commands and the Claude Code commands, `/project ` its subcommands; nothing is hinted for arguments. Subcommands need core 0.7.0+ (`listCommands()` with `subcommands`); the list is read at most once a second while typing. Claude Code commands run as `/claude <command>` (forwarded to the open chat as `/<command>`).

Display, modelled on Claude Code's terminal UI:

Caps: 50 items, 200 code points of text per item, ids of 32 characters. The engine emits one `plan` UI event per change and the runner snapshot carries the optional `plan`, so a reattached chat shows its widget at once. The widget is collapsed to three rows: `☰ Plan 3/7 ▰▰▱▱▱▱▱`, the active item (a braille spinner while the turn runs, `›` when idle) and the next open item (`○`); below 24 rows it is one `segmentBar` row; it is hidden below 12 rows (the tiny tier) or 30 columns, with no plan, when everything is done and the turn is idle, when the plan is stale (a turn ended without touching it while it still had open items), and after a reset. A finished plan is dropped at the next turn start. A completed item flashes `✓ <item>` at the header's right for 3 s; nothing animates while idle. With the mouse preference on, a click on the widget expands it in place (the header and every item, windowed, at most min(10, the rows the header gives the plan) rows, and at least two). Ctrl+O has a `Plan` section before the changed files. The transcript prints notes instead of the rows: `☰ Plan · 7 steps` for a new plan, `✓ <item>` for each completed item (at most 3, then `✓ +N more done`), `☰ Plan +2 steps` for added items and `✓ Plan done · 7/7` at the end; nothing for moves, edits or deletions.

- Input: ↑/↓ walk through the messages sent in this run of yena (the draft comes back after the newest); Shift+↑/↓ still scroll. Enter while Claude answers sends the message into the running turn, as Claude Code's own REPL does (`ChatSession.steer`: a user message with `priority: 'next'`, so Claude Code folds it in at the next step instead of after the turn); it shows in the transcript at once. When it arrives too late for the turn, Claude Code answers it in a turn of its own: a result with `queued_turn_count > 0` (`queuedTurns`) keeps the chat running until the last result. A background chat sends a `steer` frame; the runner sends it as a new message when its turn has just ended, and answers `steer-failed` when it can do neither, which puts the text back into the queue (or the draft when nothing runs). The queue (`↳ queued: …`, at most 20) is the fallback: while the turn is being interrupted, when steering is refused, and for messages after a queued one, so they keep their order; it is sent as one message when the turn ends, and goes back into the draft if the turn was interrupted or failed with a limit or context error.
- Editing: Ctrl+A/E (line start/end), Ctrl+U/K (kill to start/end), Ctrl+W and Alt+Backspace (kill word back), Alt+D (kill word forward), Ctrl+Y (put the last kill back), Alt+B/F and Ctrl/Alt+←/→ (word moves), Ctrl+_ or Ctrl+/ (undo). Ctrl+R searches the sent messages (type to narrow, Ctrl+R again for older, Enter takes the match into the input, Esc cancels). Ctrl+G opens the draft in the external editor. `@` lists project files (skipping node_modules, .git, build output, .yena and secret-looking names; read on the first `@`), ↑↓ choose, Tab or Enter completes; Claude Code reads mentioned files, images included.
- Vim mode (`Input mode` setting): Esc enters NORMAL (`-- NORMAL --` under the input), `i a I A o O s S C` and `:` go back to INSERT; `h l 0 ^ $ w e b` move, `x X D dd dw de db d$ cc cw yy p u` edit, `j k` walk the history, Enter sends. Esc in NORMAL, or while Claude answers, does what Esc does in the chat.
- Permission prompt: a file tool's change with a preview (Edit, MultiEdit, NotebookEdit, Write) is shown as a file card at the prompt width (columns − 4), drawn by the same renderer without the header row; the preview is cut by the same budget as before, then `… [preview truncated]` (`previewCardRows` in `src/ui/file-card.ts`, `previewRows` in `src/ui/prompt-state.ts`).
- Ctrl+O opens the whole transcript of the chat (prompts, answers rendered as Markdown with code blocks in full, thinking, every tool call with its input and up to 400 lines of its result; a file change is shown as its whole file card instead, without the row cap, read from the session file's tool result), read from the session file and wrapped once per width (`viewerRowsOf`), so scrolling stays smooth on long chats; ↑↓ or j k scroll, space/b by a page, g/G to the ends, Esc, q or Ctrl+O close. When the last turn changed files it ends with the section `Changed in the last turn` (see Turn summary).
- Turn summary (`src/ui/turn-summary.ts` over `turn-end.summary`, built by the engine with chat's `TurnStats`): when a turn ends, one row is printed after its last block: `✓ 2m 14s · 3 files changed +42 −7 · 5 tools · ↓ 18k tokens · ctrl+o files` (`✓` in ok, `✗` in error). An interruption reads `✗ interrupted …` in warn and replaces the `Interrupted.` notice; the other failures keep their message row and get the `✗` row after it. It is shown when the outcome is not ok, the turn used a tool, or it took 30 s or more. The duration is the engine's clock from the turn's start to its end; tools count each call once, subagent calls included; the tokens are output tokens; the files and their `+`/`−` are the ones the file cards show (Edit, MultiEdit, Write and NotebookEdit, subagents included; failed calls are not counted); at most 200 files are sent, and `filesTotal` counts all. When the row does not fit it drops the `ctrl+o files` hint, then the tokens, the tools, and the file counts last. Ctrl+O's viewer ends with `Changed in the last turn`: one row per file (`✎ path  +12 −3`, the path relative to the project and cut in the middle), `… +N more` past 200. The chat view keeps only the last summary, so after a reattach it is missing until the next turn; an older runner sends none and the row is not shown.
- Mouse (needs a core whose `ViewHost` provides `subscribeMouse`; feature-detected, older cores lack it, `src/ui/view-mouse.ts`): a left click in the input moves the cursor, only while it is editable (not during permission or question prompts, the Ctrl+O viewer, Ctrl+R search, a pending mode switch or the Waiting row; in Vim NORMAL it lands on a character). The wheel scrolls the Ctrl+O viewer by 1 line while it is open; otherwise core scrolls the transcript. A click can land on the wrong row if a key that changes the input's line count has not been rendered yet.
- Live Bash output (needs core 0.5.0+): while a foreground Bash call runs for 500 ms or more and the chat has focus, the console panel opens (without taking focus) and shows `$ <command> · Ns` plus the tail of the command's output as it is written (polled every 200 ms); it closes when the call ends and core's 3 s grace then applies. Only one panel attempt is made per Bash call, and only when the chat has focus and the panel is free. The SDK sends no start or progress events for a foreground Bash call, so the chat watches Claude Code's own output file (`<tmp>/claude-<uid>/<project>/<session>/tasks/<task>.output`, an undocumented layout) and binds it to a call only when exactly one candidate matches. For that, chats start Claude Code with `CLAUDE_CODE_TMPDIR=/tmp/yena-claude-<uid>` (created 0700, must be owned by you and closed to others, else live output is off and `shell tmp unavailable` is logged). The same env sets `npm_config_cache` to `npm-cache` in the CLI's tmp dir (the sandbox does not let npm write `/root/.npm/_cacache`, and npm then fails with a bare `ENOENT`) and `NODE_USE_ENV_PROXY=1`, so `node` `fetch` in Bash goes through the sandbox's proxy. This also moves Claude Code's other temp files, such as background task output, there; `ask` and `bin/claude` are unchanged. Output lines are scrubbed like all other text (at most 200 lines / 32 KiB kept, lines cut at 1024 characters, the last line shown once its newline arrives). Not shown: parallel Bash calls (ambiguous), background Bash, more than 4 simultaneous calls, subagent Bash.

- Display: answers are rendered as Markdown by `src/ui/markdown-parse.ts` (a linear block parser and inline tokenizer: paragraphs keep their line breaks; headings, nested lists up to 6 levels with `•`/`◦`/`▪` markers, aligned numbers and task boxes, quotes with a rule per level, rules, fenced code with `~~~`, longer markers and fences indented in a list, GFM tables) and `src/ui/markdown.ts` (rows already fitted to the width; closed blocks are cached by source and layout, so the streaming tail re-renders only the block that changed). Headings use the `heading` tone (H1/H2) or bold, inline code the `code.inline` tint (backticks stay at colour depth `none`), links are the label in the `link` tone followed by a muted ` (url)` (only the label when it equals the url; no OSC 8 is ever written), bold, italic and strikethrough are attributes. Fenced code is drawn by core's `renderCodeFrame`: `╭─ typescript ──── copy ─` over the full width, a `│ ` gutter, `│↪` on the rows of a wrapped line (wrapped between tokens, a token is split only when it alone is wider than the row), a bottom border and no right edge; the language goes through `fenceLanguage` (`src/ui/highlight.ts`: names, extensions and aliases such as `sh`, `shell`, `golang`, `c++`) to the same highlighter as the file cards (syntax colours at truecolor and 256 only; an unknown language or a block over its caps stays plain). In the chat (and the resumed history) the top border ends with an underlined `copy`, and a click on that row copies the code as written (scrubbed, without the frame; needs a core with print actions); the gallery and plain forms never show it, and with the mouse preference off the click does nothing. A printed code block shows at most 120 rows (`CODE_BLOCK_ROWS`), then `╰─ ⋯ +N lines ─…` (copy still copies all, the Ctrl+O viewer shows all). Tables (`src/ui/markdown-table.ts`) are laid out to the chat width: a framed box with a bold header row, cells wrap (columns keep at least 3 cells), too narrow means one `Header: value` record per row, at most 200 body rows then `⋯ +N rows`; pipes inside code spans do not split cells; tables with more than 64 columns stay plain text. The live streaming tail (`liveTail`, wrapped to the chat width minus 1, without the `copy` label) draws an open fence with its top border and no bottom border; its finished lines are highlighted, the partial last line is plain until its newline, and a table without its separator row stays a paragraph. When the tail is longer than its 16,000-character window, a code fence opened before the window still frames the code in it. Printed answers are laid out again at each transcript width; an older core, which ignores a `render` that returns text and actions, keeps the layout of the printing width. Limitations: tables inside lists or blockquotes are not recognised, `<br>` and setext headings are not interpreted, and CJK or emoji at a column width of 1-2 cells may exceed it by one cell.

- Syntax highlighting in file cards: highlight.js 11.12.0 (`package.json`, exact pin, zero dependencies, no install script) is loaded lazily by `src/ui/highlight.ts`. `preloadHighlighter()` runs when the chat mounts and when the `diff`, `tools` and `markdown` gallery sections load; it imports `highlight.js/lib/core` and the 26 languages in `HIGHLIGHT_LANGUAGES` once, on its own instance. Until that resolves, or after a failed import (not logged yet), cards, Bash command rows and answers' code blocks render without syntax colours. The language of a file comes from `languageFor(path, firstLine)`: an extension table, basenames (`Dockerfile`, `Makefile`, `.bashrc`, `.profile`, `.zshrc`), then a shebang on the first line; a code fence's tag from `fenceLanguage(tag)`. Highlighting runs per contiguous block between folds and is skipped for a block over 2000 lines, 64 KiB or a line over 1000 characters; at most 256 KiB is highlighted per card. Only `src/ui/` imports it (the background runner does not).

- The live area is kept shorter than the terminal (rows-3, rows-1 under 12 rows); on tiny terminals the streaming tail can shrink to nothing and several tools show as `N tools running`; the prompt and the status bar share the live budget (the permission prompt tier is picked from it, `PROMPT_ROWS` in `src/ui/prompt-state.ts`).

## Colours
The chat takes its colours from core's kit theme (`src/ui/sgr.ts`): each formatting call reads the table for the active depth once and uses its semantic keys (`error`, `ok`, `warn`, `accent`, `muted`, `added`, `removed`, `surface`, the `code.*` keys for Markdown code, and the attribute codes), so the module writes no SGR codes. The roles: user line on `surface`; thinking, `(interrupted)` and the file card's context, fold and metadata lines on `muted`; file card additions and removals on `added` and `removed`, their row tint on `addedBg`/`removedBg` and changed words on `addedWord`/`removedWord` (tints and syntax colours only at truecolor and 256; the `code.*` tones carry the highlighted code, mapped from highlight.js scopes by `HLJS_SCOPE_TONE`); tool errors on `error` (the `✗` mark, the reason row, a failed Bash's `exit N`), the `✓` mark on `ok`, refusals, durations and details on `muted`, the family glyphs on `muted`; warnings on `warn`; the plan widget's `✓` on `ok` and its item text on `muted`, the status bar's activity on `running`, its meter on `muted`, `warn` from 60 % and `error` from 85 %, the summary's counts on `added` and `removed`; Markdown headings on `heading`, links on `link`, inline code on `code.inline`, list markers on `accent`, quote text on `muted`, frames and rules on `frame`, strings, numbers, keywords and comments on the `code.*` tones. The depth is core's `colorDepth()`: `NO_COLOR` (non-empty), the Colours setting off (Appearance tab, `colors` in `appearance.json`) or `YENA_COLOR` / `COLORTERM` / `TERM` decide it, and it is detected once per process. Dark theme only.

Gallery: `ui gallery chat [--width <n>] [--depth <depth>]` (core's command) shows the chat's pieces (user line, assistant Markdown, thinking, Edit diff, a failed Bash call, notice, warning, error) at a width, with the depth shown. The `chat`, `diff`, `tools`, `status`, `plan`, `layout` and `markdown` sections are registered when the plugin loads (`diff`, title `File changes`, shows file cards: an Edit with a word diff and a fold, side by side from 160 columns, a new file, and a long change capped); `markdown` (title `Assistant text`) shows headings, nested and task lists, a quote, inline styles, a TypeScript and a bash block, a wrapped long line, a table, a capped block and the thinking row; `tools` (title `Tool calls`) shows tool rows: a running row, Read, a fold of reads and searches, Glob, a Bash call with a tail box, a failed Bash with `exit 1` and 12 s, a multi-line Bash, an Edit with 2.1 s, an Edit error, a denied Bash, WebFetch, an Agent with activity, yena's `run_command`, an MCP tool and a failed TodoWrite; `plan` (title `Plan widget`) shows the summary at the column tiers (40, 80 and 120 columns, running and idle) in the tall tier, a note in the other tiers, the line mode, the expanded window (`--rows` sets the tier), the flash, all done and the transcript notes; `layout` (title `Chat layout`) draws a mock frame (plan, agent boxes, tail, running tools, prompt rule, status bar) through the real `headerLayout` and `liveLayout` at `--width` and `--rows`; `status` (title `Status bar and turn summary`) shows the bar at the column tiers (40, 80, 120 columns) for idle, running, awaiting approval and high context, then the summary row for ok, interrupted and error; if registration fails a `gallery section skipped` warning is logged and the plugin keeps working.

Through the injected `host.log` (scope of the host's logger; `src/log.ts` is a noop logger when the host gives none).
- debug `plugin loaded`; warn `gallery section skipped` {section?, err?} (a gallery section did not register).

## Development

From `modules/chat`: `npm install && npm run typecheck && npm test` (`npm test` runs the `.ts` and `.tsx` tests under `tests/`). `tsc` and `tsx` come from the host's `node_modules`, so this works inside the host tree. `tests/index.test.ts` covers the plugin, `tests/kit-boundary.test.ts` that `src/index.ts` and `src/public.ts` never reach react, ink or `kit/ui`, and `tests/public-ui.test.ts` the UI entry's names.
Every `.tsx` file must start with `import React from 'react'` (yena runs tsx from `/app`).
`bin/install` runs `npm install --prefix <module>` when `npm ls --omit=dev --depth=0` finds highlight.js missing or at another version. A failed install prints `Failed to install module dependencies` and the chat runs without syntax colours; nothing else fails.
